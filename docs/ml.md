# ML/LLM-дизайн

## Разделение задач по типу решения

Правило выбора: **чем выше цена ошибки и требование объяснимости, тем проще должен быть механизм.** Отсюда распределение:

| Задача | Механизм | Почему именно так |
|---|---|---|
| Нормализация, дедупликация по хешу | Правила | Детерминированная задача, модель не нужна |
| Маскирование PII | Правила + NER | Структурированные сущности (карта, email, телефон) ловятся регулярками надёжнее модели; имена и адреса — только NER |
| **Оценка риска** | **Только правила** | Ошибка = небезопасный ответ пользователю. Нужны объяснимость постфактум и изменение за минуты без переобучения |
| Классификация темы | Классическая ML | Много размеченных данных, стабильный набор классов, нужна latency в десятки мс |
| Приоритет / SLA-риск | Классическая ML | Табличные признаки (канал, тариф, история), градиентный бустинг |
| Поиск похожих тикетов и статей KB | Embeddings + retrieval | Семантическое сходство, точное совпадение слов не работает |
| Кластеризация при инцидентах | Embeddings + онлайн-кластеризация | Схлопывает всплеск в один кластер |
| **Генерация ответа** | **LLM** | Единственная задача, где нужна свободная генерация текста |
| Суммаризация тикета для оператора | LLM | Терпима к неточности: оператор видит исходник рядом |

### Где LLM использовать не стоит

- **Оценка риска и принятие решения об автозакрытии.** LLM недетерминирован, уязвим к prompt injection (текст тикета — недоверенный вход) и не даёт стабильного объяснения. Ровно ту функцию, где ошибка максимально дорога, отдавать вероятностной модели нельзя.
- **Классификация темы на «горячем» пути.** Не укладывается в 500 мс и стоит на два порядка дороже классификатора при сопоставимом качестве на 7 классах.
- **Извлечение PII.** Пропуск сущности здесь — утечка. Регулярки дают предсказуемый recall на структурированных данных.
- **Массовая обработка при инциденте.** 20k тикетов за 10 минут через LLM — это стоимость и rate limit; дедупликация решает задачу дешевле.

## Модели: происхождение, данные, метрики выбора

| Модель | Откуда берётся | Обучающие данные | Метрика выбора |
|---|---|---|---|
| Классификатор темы (v0, baseline) | Обучаем внутри: TF-IDF + LogisticRegression | 5–10k размеченных исторических тикетов | macro-F1; latency p95 |
| Классификатор темы (v1) | Открытый энкодер (`ru-en-RoSBERTa`, `rubert-tiny2`), дообучаем внутри | 20–50k размеченных тикетов | macro-F1, ECE (калибровка), latency p95 |
| Эмбеддинги для retrieval | Открытая модель без дообучения на старте | — | Recall@5 на парах «тикет → правильная статья KB» |
| NER для PII | Открытая (Natasha / spaCy ru), дообучение при нехватке recall | 1–2k тикетов с размеченными сущностями | Recall по каждому типу сущности |
| Приоритизация / SLA-риск | Обучаем внутри, градиентный бустинг | Табличные фичи + исход тикета | PR-AUC |
| Генерация | Внешний API (Claude) | Не обучаем | Grounding rate, доля правок оператора |

**Калибровка важнее точности.** Политика принимает решения по порогу уверенности, поэтому нужно, чтобы `confidence = 0.9` действительно означало ~90% правоты. Модель с точностью 0.88 и хорошей калибровкой полезнее модели с 0.91 и уверенным враньём: первая корректно уходит в escalate там, где сомневается. Меряем ECE и калибруем (Platt / isotonic) на отложенной выборке.

Ключевой критерий выбора порога — **precision автозакрытия при заданном покрытии**, а не общая accuracy. Ошибка «отдали оператору лишний тикет» стоит 150 ₽; ошибка «закрыли неверно» стоит CSAT, reopen и потенциально нарушенный SLA.

## Baseline и порядок запуска

Порядок намеренный: каждый шаг даёт измеримую отсечку, ниже которой следующий шаг не имеет смысла.

1. **Правила по ключевым словам.** Нижняя граница качества и рабочий fallback. Если ML не бьёт этот baseline заметно — ML не нужен.
2. **TF-IDF + линейная модель.** ← *реализовано в PoC.* Обучается за секунды, считается за миллисекунды, даёт понятную планку.
3. **Дообученный энкодер.** Запускать только если п.2 упирается в потолок на реальных данных.
4. **Retrieval поверх открытых эмбеддингов** без дообучения.
5. **LLM для генерации** — последним, когда классификация и маршрутизация уже стабильны.

### Что показал baseline в PoC

TF-IDF по символьным n-граммам (3–5, `char_wb`) + LogisticRegression, 5-fold CV на 70 синтетических тикетах:

```
macro-F1 = 0.724 ± 0.111
```

Символьные n-граммы вместо пословных выбраны из-за русской морфологии и опечаток в чате — иначе нужен лемматизатор, а это лишняя зависимость в PoC.

**Как честно читать это число:** 0.72 на 70 синтетических примерах — свидетельство того, что пайплайн запускается и метрика считается, а **не** оценка качества будущей системы. Датасет писался вручную под демонстрацию, темы в нём разделены чище, чем в реальном потоке; при этом примеров так мало, что разброс между фолдами (±0.11) сопоставим с разницей между хорошей и плохой моделью. На реальных данных ожидаю и другой уровень, и другую структуру ошибок.

Практический вывод для PoC один: политика **не полагается на модель в одиночку**. Правила риска имеют veto, а порог `confidence ≥ 0.60` для автоответа отсекает случаи, где модель неуверенна.

## Разметка исторических данных

Без разметки не запускается ни классификатор, ни оценка качества. План на MVP:

1. **Бесплатная разметка из логов.** Текущие теги операторов и очереди, куда тикеты попадали вручную — это уже слабая разметка на десятки тысяч тикетов. Шумная, но бесплатная; годится для первой версии классификатора.
2. **Ручная разметка золотого набора.** 2–3k тикетов, стратифицированная выборка по каналам и темам. Двойная разметка с замером согласованности (Cohen's κ); при κ < 0.7 проблема в инструкции, а не в разметчиках — переписываем и размечаем заново. Это единственный набор, по которому меряется качество.
3. **Отдельная разметка риска.** Не «тема», а бинарное «можно ли отвечать автоматически». Размечает не аутсорс, а команда поддержки вместе с юристом — это по сути формализация политики компании.
4. **Активное обучение.** После запуска в разметку уходят тикеты с низкой уверенностью и те, где оператор переписал черновик — то есть примеры, на которых модель ошибается.
5. **Обязательная случайная выборка автозакрытых тикетов в разметку.** Без неё возникает петля: размечается только то, что не автоматизировали, модель дообучается на всё более сложных случаях, а качество на лёгких не измеряется вообще — потому что их никто не смотрит. Чем лучше работает автоматизация, тем слепее становится контроль за ней. Лечится единственным способом: фиксированная доля автозакрытых тикетов (например 1%) уходит человеку на разбор независимо от уверенности модели.
6. **Автоматически закрытые тикеты не попадают в корпус retrieval до проверки человеком.** Иначе ошибочный ответ становится прецедентом, который извлекается для следующего похожего обращения, — система усиливает собственную ошибку через свой же выход.
7. **Правки операторов как непрерывный сигнал.** В suggest-режиме каждый принятый/отклонённый/изменённый черновик — бесплатная разметка. Ради этого suggest-режим и стоит в плане раскатки перед автозакрытием.

Разметку версионируем вместе с датасетом: изменилась таксономия тем — это новая версия датасета и новая модель, а не молчаливое переобучение.

## Валидация качества

| Уровень | Что меряем | Инструмент |
|---|---|---|
| Классификация | macro-F1, per-class recall, ECE | Отложенная выборка золотого набора |
| Retrieval | Recall@k, MRR | Пары «тикет → статья, которую использовал оператор» |
| Правила риска | **Recall по рискованным тикетам** | Ручной разбор всех FN: пропуск здесь — это то, ради чего строился весь слой |
| Генерация | Grounding (нет утверждений вне KB), safety, доля правок оператора | LLM-as-judge + ручной аудит выборки |
| Политика в целом | Precision автозакрытия, доля покрытия | Shadow-режим на реальном потоке |
| Регрессии | Набор из ~50 «золотых» кейсов, включая prompt injection | Прогон в CI на каждое изменение промпта, порога или правил |

**Shadow-режим — основной инструмент валидации до запуска.** Система принимает решения на реальном потоке, ничего не отправляя. Сравниваем её решения с тем, что реально сделали операторы, и получаем честную оценку precision автозакрытия без единого риска для пользователя.

В PoC роль регрессионного набора играют тесты: [test_policy.py](../poc/tests/test_policy.py) фиксирует инварианты безопасности (высокий риск блокирует автоответ независимо от уверенности модели), [test_pipeline.py](../poc/tests/test_pipeline.py) — end-to-end сценарии, включая prompt injection и деградацию LLM.

## Обработка низкой уверенности

Низкая уверенность — не ошибка, а штатный сигнал. Каскад:

```
confidence < 0.35            → escalate, черновик не генерируется
0.35 ≤ confidence < 0.60     → suggest, черновик оператору
confidence ≥ 0.60            → кандидат на auto_reply,
                               если тема в safe-list И retrieval-скор ≥ порога
```

Три дополнительных правила поверх порогов:

- **Правила риска перебивают любую уверенность.** `confidence = 0.99` на теме «возврат средств» всё равно даёт escalate.
- **Слабый retrieval блокирует автоответ.** Высокая уверенность в теме при отсутствии релевантной статьи KB означает «я знаю, о чём тикет, но отвечать нечем» — это suggest, не auto_reply.
- **Пороги — конфиг, не константы.** Они настраиваются по shadow-данным под целевой precision и пересматриваются при каждом обновлении модели.

Отдельный класс — **near-miss между двумя темами** (разница вероятностей топ-1 и топ-2 меньше 0.15). Формально уверенность может быть выше порога, но модель по сути выбирает монеткой. Такие тикеты идут в suggest и приоритетно попадают в разметку.

## Стоимость инференса

| Компонент | Где считается | Порядок стоимости |
|---|---|---|
| Классификатор + правила + retrieval | Свои CPU-инстансы | Пренебрежимо мал относительно LLM |
| Генерация | Внешний API | Основная статья расходов |

Рычаги контроля стоимости, встроенные в дизайн:

1. **LLM вызывается не для всех тикетов**, а только после решения политики — escalate-тикеты идут к оператору без генерации.
2. **Дедупликация при инцидентах**: один ответ на кластер вместо 20k вызовов.
3. **Кеш ответов** для повторяющихся FAQ-формулировок.
4. **Малая модель для суммаризации**, крупная — только для клиентских ответов.
5. **Дневной бюджет с автоматическим отключением автогенерации** при превышении — см. [monitoring.md](monitoring.md).
