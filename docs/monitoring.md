# Мониторинг и эксплуатация

Наблюдаемость строится вокруг одного вопроса: **можем ли мы в любой момент доказать, что система всё ещё безопасно решает исходную задачу?** Не «работают ли сервисы», а «не начали ли мы тихо вредить».

## Технические метрики

| Метрика | Разрез | Почему важна |
|---|---|---|
| Латентность горячего пути, p50/p95/p99 | По шагам пайплайна | Прямой SLO — 500 мс. Разбивка по шагам показывает, кто именно съел бюджет |
| RPS входящих тикетов | По каналам | Детектор инцидента: всплеск ×10 = включается режим дедупликации |
| Глубина и возраст очереди генерации | — | Растущий возраст = генерация не успевает, скоро поедет SLA |
| Error rate и таймауты LLM API | — | Вход в деградацию |
| Состояние circuit breaker | — | Бинарный флаг «автозакрытие включено / выключено» |
| Доля деградированных ответов | — | Сколько черновиков собрано шаблоном вместо LLM |
| Latency и Recall@k векторной БД | — | Падение retrieval тихо убивает автоответы |

## ML-метрики

| Метрика | Как считается | Норма |
|---|---|---|
| Распределение предсказанных тем | Доля каждого класса, скользящее окно | Сравнение с исторической базой |
| Распределение confidence | Гистограмма, p10/p50/p90 | Сдвиг влево = модель «поплыла» |
| Доля low-confidence | `confidence < порога` | Рост = дрейф входа или деградация модели |
| Доля срабатываний каждого правила риска | По правилам | Резкое изменение = новый паттерн обращений |
| Precision автозакрытия | Ручной аудит выборки + reopen как прокси | Главная метрика безопасности |
| Grounding rate генерации | LLM-as-judge на выборке | Доля ответов без утверждений вне KB |
| Доля правок черновика оператором | Из suggest-режима | Прокси-качество генерации, бесплатный сигнал |
| Recall правил риска | Ручной разбор escalate-тикетов и жалоб | Пропуск здесь — то, ради чего строился слой |

## Продуктовые / бизнес-метрики

Пороги и North Star — в [product.md](product.md). Здесь — как они снимаются в эксплуатации:

| Метрика | Источник | Частота |
|---|---|---|
| Доля тикетов, закрытых без оператора | Аудит-лог: `decision = auto_reply` без последующего reopen | Реальное время |
| Reopen rate | Тикеты, переоткрытые в течение 72 ч, в разрезе `auto_reply` / `suggest` / оператор | Ежедневно |
| CSAT | Опрос после закрытия, разрез по типу решения | Еженедельно (нужен объём) |
| SLA breach rate первого ответа | Время до первого ответа vs 15 минут | Реальное время |
| Экономия часов операторов | Автозакрытые тикеты × 8 минут | Еженедельно |
| Средняя стоимость обработки тикета | (LLM + инфра + операторы) / тикеты | Еженедельно |

Ключевой разрез для всех метрик — **тип решения**. Средний CSAT по всем тикетам скроет проблему: автоответы могут проседать, а рост доли простых тикетов в автоматизации подтянет среднее вверх.

## Стартовые алерты

Набор намеренно маленький: каждый алерт должен требовать действия, иначе его перестанут читать.

| Алерт | Условие | Severity | Действие |
|---|---|---|---|
| Латентность горячего пути | p95 > 400 мс, 5 мин | P2 | Разбор по шагам, скейл |
| **Reopen rate автоответов** | > 12% (base 9% + 3 п.п.), скользящие 24 ч | **P1** | Автоматическое отключение автозакрытия |
| CSAT автоответов | < 4.0, недельное окно | P1 | Стоп-раскатка, разбор выборки |
| SLA breach rate | > 5%, 1 ч | P1 | Проверка очереди, ручное распределение |
| LLM error rate | > 20%, 5 мин | P2 | Проверить circuit breaker, подтвердить деградацию |
| Circuit breaker разомкнут | > 15 мин | P2 | Автозакрытие выключено, растёт нагрузка на операторов |
| Дневной бюджет LLM | > 80% / > 100% | P3 / **P1** | Предупреждение / отключение автогенерации |
| Дрейф распределения тем | PSI > 0.25 к baseline | P3 | Разбор: инцидент или дрейф |
| Всплеск входящих | ×5 к базовой линии, 10 мин | P2 | Включение инцидент-режима с дедупликацией |

**Reopen rate автоответов — единственный алерт с автоматическим действием.** Всё остальное будит человека; здесь система выключает автозакрытие сама, потому что каждая минута промедления — это новые пользователи с плохим ответом.

## Деградация модели или изменение потока?

Самая частая ошибка разбора: увидеть падение метрики и начать чинить модель, когда изменился вход. Разделяем по трём осям.

**1. Что именно сдвинулось — вход или выход.**

| Наблюдение | Диагноз |
|---|---|
| Распределение входа стабильно, качество падает | Деградация модели или обновление промпта |
| Распределение входа сдвинулось, качество на *старых* сегментах стабильно | Изменение потока — модель в порядке |
| Сдвинулось и то и другое | Новый сегмент, которого не было в обучении |

Практический тест: считаем метрики отдельно на **стабильном подмножестве** — тикетах, чьи признаки попадают в исторический диапазон. Если там качество не упало, проблема во входе.

**2. Что менялось у нас.** Каждое решение в аудит-логе несёт `model_version` и `policy_version` ([audit.py](../poc/src/support_triage/audit.py)). Метрики строятся в разрезе версий: падение, совпадающее с релизом, — это регрессия, а не дрейф.

**3. Внешние маркеры.** Всплеск + рост доли одной темы + всплеск на статус-странице = инцидент, а не деградация. Сюда же: релизы продукта, маркетинговые рассылки, сезонность.

**Канареечная выборка.** 1–2% трафика всегда обрабатывается предыдущей версией модели. Если новая просела, а канарейка нет — регрессия наша. Если просели обе — изменился поток.

## Мониторинг стоимости LLM

| Что | Разрез |
|---|---|
| Токены (вход/выход) и стоимость | По типу задачи: ответ / суммаризация / post-check |
| Стоимость на тикет | Тренд; сравнение с 150 ₽ операторской обработки |
| Доля тикетов, дошедших до LLM | Прямой рычаг: растёт — растёт счёт |
| Стоимость на автоматически закрытый тикет | Единица «сколько стоит одна единица ценности» |
| Cache hit rate | Эффективность кеша повторяющихся FAQ |
| Прогноз до конца месяца | По текущему run-rate |

Защиты от неконтролируемого роста:

1. **Дневной и месячный бюджет** с жёсткой отсечкой: при исчерпании автогенерация выключается, система переходит в режим «только маршрутизация».
2. **Rate limit на воркеры генерации** — всплеск не превращается в счёт.
3. **Алерт на аномальный рост средней длины промпта** — часто это баг (в промпт утекла вся история переписки), а не рост нагрузки.
4. **Дедупликация при инцидентах** — главный рычаг: 20k тикетов кластеризуются в единицы ответов.

## Как отслеживается, что реальная задача решается

Технические метрики могут быть зелёными, а задача — не решаться. Три способа поймать это:

**1. Метрика конечного результата, а не активности.** Считаем не «сколько тикетов обработано автоматически», а **сколько закрыто автоматически и не переоткрыто, при неухудшении CSAT**. Автоответ, после которого пользователь написал снова, — это отрицательная ценность: он потратил время пользователя и всё равно занял оператора.

**2. Регулярный ручной аудит.** Каждую неделю случайная выборка (~50 тикетов) автоматических решений разбирается вручную по чек-листу: ответ корректен по существу, не выдумал фактов, тон уместен, не следовало ли отдать оператору. Это единственный способ поймать проблемы, на которые нет метрики.

**3. Контроль голосом пользователя и оператора.** Доля жалоб на автоответ; доля тикетов, которые оператор пометил как «не следовало автоматизировать» — кнопка обратной связи в интерфейсе оператора. Оператор видит то, чего не видит ни одна метрика.

**Контрольная группа на всё время пилота.** 5% трафика обрабатывается полностью вручную. Без неё невозможно отличить «система улучшила CSAT» от «CSAT вырос сам по другой причине». Сравнение с прошлым периодом такой гарантии не даёт.
